# Безопасность Elonbot

## Защита входа

Сервер принимает `X-Forwarded-For` только от точных адресов в `TRUSTED_PROXY_IPS`. Цепочка разбирается справа налево до первого недоверенного адреса. Некорректный заголовок не используется; IP нормализуются, включая IPv4 в IPv6. Не разрешайте доверие произвольным посетителям и не подставляйте этот заголовок из параметров запроса.

Для Caddy на том же VPS используйте `HOST=127.0.0.1`, `PORT=8000`, `TRUSTED_PROXY_IPS=127.0.0.1,::1` и `reverse_proxy 127.0.0.1:8000`. Это значения приложения по умолчанию. Внешние 8000 и 5432 должны быть закрыты, а публичный сайт доступен только через HTTPS-прокси. Если перед Caddy есть CDN, отдельно настройте его доверенные адреса в Caddy; приложение не должно доверять произвольному левому элементу цепочки.

За иным прокси сначала выясните фактический адрес непосредственного узла и правила формирования заголовков. Без этого безопаснее оставить `TRUSTED_PROXY_IPS` пустым, однако посетители общего прокси тогда разделяют HTTP-лимит входа. Для Render/контейнера нужен `HOST=0.0.0.0`; доступ к backend ограничивается средствами платформы.

Обычный и административный вход имеют отдельные ограничения HTTP: 30 запросов в минуту с адреса посетителя. Дополнительно PostgreSQL хранит до 10 шагов входа и до 3 запросов кода за окно 10 минут на пользователя. Новая ссылка, отключение и перезапуск приложения не сбрасывают это окно. Ограничения Telegram продолжают действовать независимо. На одного пользователя допускается одна незавершённая авторизация; общий предел 100 включает ещё подключающиеся клиенты. Это предел ресурсов авторизации, а не лимит пользователей или публикаций.

## Telegram-сессии и данные

Пользовательские тексты подключения и справки на обоих языках говорят: сервис не сохраняет историю переписок в других чатах и не отслеживает новые сообщения в них. При этом для выбора групп получает список чатов и сведения о группах, а сообщения, отправленные самому боту для объявлений или поддержки, обрабатываются и могут сохраняться. В приглашении написать администратору отдельно указано, что переписка с поддержкой сохраняется и доступна администраторам. Формулировка «вообще ничего не хранится» не соответствует работе приложения.

Подключённая MTProto-сессия действует от имени пользователя; она не является разрешением исключительно на выбранные группы. Приложение ограничивает свои операции и проверяет владельца, но кража пригодной сессии позволяет обойти ограничения приложения. AES-256-GCM защищает отдельную утечку БД, однако не компрометацию процесса с ключом расшифрования. На странице входа это объясняется на узбекском и русском.

Пользователь может отключить аккаунт в боте: **Настройки → Telegram-аккаунт → Отключить**. Приложение отзывает свою сессию и удаляет её запись. Если бот недоступен, завершите сессию **Elonbot** в **Telegram → Настройки → Устройства**. Следующее обращение к отозванной сессии остановит отправку. Отключение сохраняет объявления и группы; оно не означает удаление всех данных.

В БД есть объявления, шаблоны, черновики, обращения в поддержку, сведения о пользователях/группах и журналы операций. Новые фото представлены ID сообщений в чате с ботом; сами файлы не записываются в БД. Старые фото могут использовать `file_id`. Пароли 2FA и коды входа явно не сохраняются. Автоматическое удаление всей учётной записи и единый срок хранения всех пользовательских данных пока не реализованы; оператор должен учитывать это при ответе на запрос об удалении. Не обещайте пользователю полное удаление после простого отключения аккаунта.

## Служба, ключи и обновление

- Используйте отдельного пользователя `elonbot` без sudo; репозиторий обновлений принадлежит `deploy`. Не запускайте приложение от root. Пример systemd с ограничением прав находится в [инструкции Ubuntu](ubuntu-vps-security-ru.md).
- `.env` — права `600`, доступ только службе и администраторам. Не публикуйте его и не отправляйте содержимое в журнал или чат. Ключ создаётся один раз из 32 случайных байтов; готового ключа в `.env.example` нет.
- Шифруйте резервные копии, ограничивайте доступ к ним и к копии ключа отдельно. Каталоги `/opt/elonbot.backup-*` содержат `.env`, поэтому также считаются секретными. Периодически проверяйте восстановление на отдельной базе.
- Отключите core dumps службы (`LimitCORE=0`), обновляйте Node.js, ОС и PostgreSQL; проверяйте состав `ADMIN_IDS`. Установка зависимостей и чтение конфигурации в скрипте обновления выполняются от пользователя службы.
- Перед установкой исправлений от 23.09.2026 замените внешнюю копию скрипта по [README](../README.md#развёртывание-и-проверки). Старый скрипт не получает собственное исправление автоматически при запуске.

## Проверка VPS после обновления

Эти команды ничего не изменяют и не выводят секреты:

```bash
sudo systemctl show elonbot -p User -p Group -p NoNewPrivileges -p ProtectSystem -p ProtectHome -p LimitCORE
sudo stat -c '%a %U:%G %n' /opt/elonbot/.env
sudo ss -lntp
sudo ufw status verbose
curl --fail --show-error http://127.0.0.1:8000/health
```

Проверьте: служба не root, `.env` — `600`, HTTP приложения слушает loopback, PostgreSQL недоступен извне. Отдельно с другого компьютера проверьте, что HTTPS работает, а порты 8000 и 5432 закрыты и по IPv4, и по публичному IPv6. Проверка исходного кода не заменяет эту проверку живого сервера.

## Если возникло подозрение на компрометацию

1. Остановите службу `sudo systemctl stop elonbot`, ограничьте доступ к серверу и сохраните защищённые журналы для расследования. Не удаляйте доказательства.
2. Через доверенное устройство уведомите затронутых пользователей о необходимости завершить сессию Elonbot в Telegram → Настройки → Устройства. Остановка сервера и смена ключа БД сами по себе не отзывают украденные сессии.
3. С доверенного устройства перевыпустите затронутый токен бота через BotFather и смените скомпрометированные пароли/ключи доступа. Смена `SESSION_ENCRYPTION_KEY` требует отдельного плана: старые данные перестанут расшифровываться; пользователям потребуется безопасное переподключение либо контролируемое перешифрование.
4. Восстановите приложение на доверенной системе, устраните причину и проверьте данные перед возобновлением. При компрометации самого сервера простого обновления исходников недостаточно.

План изоляции сессий в отдельном сервисе может уменьшить поверхность доступа при росте проекта, но не устраняет полномочия самих MTProto-сессий.
