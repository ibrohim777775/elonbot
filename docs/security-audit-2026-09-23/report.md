# Проверка безопасности Elonbot — 23 сентября 2026

**Статус после аудита:** четыре описанных ниже дефекта исправлены в рабочем коде. Подробности и проверки — в [отчёте об исправлениях](remediation.md). Фактический VPS не обновлялся в рамках этой работы.

Ниже сохранена исходная оценка коммита `cf70065` до исправлений. Изменений рабочего кода, серверных настроек и реальных Telegram-сессий в ходе первоначального аудита не делалось. Было выявлено четыре недостатка: два с высоким приоритетом, два со средним. Утечка аккаунтов или обход авторизации этим аудитом не установлены.

Он специально подтверждает текущее ошибочное поведение, поэтому после исправлений его ожидания потребуется изменить.

Исторический сценарий `verify.ts` предназначен только для отдельного чистого checkout коммита `cf70065` до исправлений. На новой версии он намеренно не проходит: уязвимое поведение устранено. Для проверки текущей версии запускайте `npm test`, включая новые `security.test.ts` и `update-script.test.ts`. Сохранённый `verification.json` относится к исходному аудиту.

Сохранённые результаты проверки зависимостей: [npm-audit-production.json](npm-audit-production.json) и [npm-audit-all.json](npm-audit-all.json). В обоих отчётах `npm audit` — 0 известных уязвимостей. Это результат базы npm на дату проверки, а не гарантия отсутствия ошибок, вредоносного кода или уязвимостей Node.js и ОС.

`npm run check` завершился успешно. Полный `npm test`: 87 тестов, 87 успешных, 0 ошибок. Существующие проверки включают подпись Mini App, истечение и одноразовость ссылок, административную авторизацию, CSRF, шифрование и изоляцию пользователей; четыре новых воспроизведения выполнены отдельно от этой серии.

## Найденные проблемы

| № | Приоритет | Проблема | Что подтверждено |
|---|---|---|---|
| 1 | P1, высокий | Некорректный URL выходит за обработчик ошибок HTTP | Неавторизованный локальный запрос вызывает `unhandledRejection`; обработчик в `main.ts` запускает остановку приложения |
| 2 | P1, высокий | Скрипт обновления запускает библиотеку приложения от root | Команда читает модуль из каталога, принадлежащего служебному пользователю; безвредный локальный модуль был выполнен |
| 3 | P2, средний | За прокси все пользователи делят лимит входов | После 30 неверных запросов корректный запрос с другим заявленным IP получает 429; воспроизведено для обычного и административного входа |
| 4 | P2, средний | Замена ссылки входа не освобождает старую попытку | Один пользователь создал 100 незавершённых попыток в макете Telegram; новый вход второго пользователя отклонён |

### 1. Некорректный URL может остановить приложение

Место: `app/server.ts:65`; обработчик завершения — `app/main.ts:79`.

`new URL(request.url, ...)` выполняется до `try`. Некорректный адрес вроде `//[` вызывает `ERR_INVALID_URL`. Поскольку HTTP-обработчик асинхронный, исключение превращается в необработанное отклонение Promise. В `main.ts` это устанавливает код завершения 1 и вызывает `stop()`, который выключает HTTP, планировщики и соединения.

Для этого запроса не нужны Telegram-аккаунт, подпись Mini App или webhook secret. В локальном воспроизведении подтверждён `unhandledRejection`. Связь с остановкой установлена по рабочему обработчику `main.ts`; весь production-процесс не запускался. Прохождение такого URL через фактический Caddy/CDN на VPS отдельно не проверялось. Автоматический перезапуск systemd сокращает простой, но сам дефект не устраняет.

Исправление: разбирать URL внутри общего `try`, возвращать 400 при ошибке синтаксиса, гарантировать перехват отклонений HTTP-обработчика. Добавить проверку, что после такого запроса `/health` продолжает отвечать и планировщик не останавливается.

### 2. При обновлении код зависимости получает права root

Место: `scripts/update-server.sh:67`, `scripts/update-server.sh:76`, `scripts/update-server.sh:78`.

Скрипт требует запуска через sudo. Подготовленный каталог передаётся пользователю приложения, затем зависимости устанавливаются от его имени. Однако последующая команда `PORT=$(cd "$STAGE" && node -e ...)` снова выполняется от root и вызывает `require("dotenv")` из подготовленной версии.

Если пакет, установочный скрипт или процесс с доступом на запись в этот каталог подменит загружаемый модуль, его JavaScript выполнится уже с полномочиями root. Это условный путь повышения привилегий при обновлении, а не найденный удалённый вход снаружи. Отчёт npm с нулём уязвимостей не исключает такую подмену.

Воспроизведение: в отдельном временном каталоге создан безвредный модуль `dotenv`, который записал локальный маркер при загрузке той же командой. Сам скрипт обновления и код с повышенными правами не запускались. Контекст root установлен анализом shell-скрипта.

Исправление: запускать чтение конфигурации через `runuser -u "$APP_USER"`, как и остальные операции с кодом проекта; запретить работу приложения от root. Проверить также привилегированное копирование `.env` в каталог, доступный для записи служебному пользователю: не следовать подготовленным там символическим ссылкам. Root должен выполнять только необходимые операции со службой, владельцами и переключением каталогов.

### 3. Лимит входов учитывает IP прокси вместо посетителя

Место: `app/server.ts:92` и `app/server.ts:125`. Документированная схема: `docs/ubuntu-vps-security-ru.md:755`.

В обоих входах ключом ограничения служит `request.socket.remoteAddress`. При схеме Caddy → `127.0.0.1:8000` приложение видит адрес прокси для разных посетителей. Ошибочные попытки учитываются до проверки токена, поэтому злоумышленнику не требуется действующая ссылка.

В локальной имитации обратного прокси 30 запросов с неверным токеном исчерпали лимит. Следующий запрос с действующей ссылкой и другим `X-Forwarded-For` получил 429. Это отдельно воспроизведено для `/account/login` и `/admin-api/session`. Их счётчики раздельные, но внутри каждого все посетители прокси используют один ключ. Вызовов Telegram при этом не было.

Исправление: корректно определять адрес клиента только за явно доверенным прокси либо ограничивать запросы на прокси. Нельзя просто доверять любому `X-Forwarded-For`: сначала нужно закрыть прямой доступ к backend и определить доверенные адреса/цепочку прокси. Дополнительно применять независимые ограничения по пользователю и токену.

Основание для схемы заголовков: Caddy устанавливает `X-Forwarded-For`, а доверие к промежуточным прокси требует настройки. [Документация Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults).

### 4. Повторные ссылки занимают общую ёмкость авторизации

Место: `app/accounts.ts:23`, `app/accounts.ts:27`, `app/telegram.ts:160`, `app/telegram.ts:168`.

Новая ссылка заменяет запись в `account_logins`, обнуляет счётчик попыток и получает новый хеш. Уже открытый MTProto-процесс входа со старым хешем остаётся в `TelegramService.pending` до истечения срока. На пользователя нет отдельного ограничения числа таких процессов. Общая ёмкость — 100 незавершённых входов.

В изолированном тесте один пользователь последовательно получил 100 ссылок и начал вход по каждой. Старые 99 процессов не были уничтожены. Для второго пользователя получен `LOGIN_CAPACITY_REACHED`.

Здесь Telegram был подменён: реальные ограничения отправки кодов и частоты HTTP-запросов могут затруднять эксплуатацию. Аудит подтверждает отсутствие освобождения ресурсов и изоляции на уровне приложения, но не утверждает, что 100 реальных кодов можно беспрепятственно запросить за секунды.

Исправление: одна незавершённая авторизация на пользователя; при перевыпуске ссылки закрывать предыдущий клиент. Сохранять ограничения частоты и неудачных попыток по пользователю независимо от замены токена. Проверку общей ёмкости и резервирование места делать совместно, с освобождением после ошибки.

## Что уже защищено

- Telegram-сессии шифруются AES-256-GCM со случайным nonce и привязкой к ID пользователя. Подмена шифротекста или владельца обнаруживается (`app/crypto.ts`).
- В базе хранятся хеши случайных ссылок входа. Пользовательская ссылка ограничена 10 минутами и расходуется после успешного входа. Административная ссылка одноразовая и действует 5 минут.
- После Telegram-входа проверяется совпадение Telegram ID с владельцем ссылки. Код и пароль 2FA используются для авторизации; явного сохранения этих полей в БД или логирования тела запроса в проверенном коде нет.
- Mini App проверяет HMAC, срок подписи и повторяющиеся параметры. Пользователь определяется по подписанным данным, а не по `userId` из тела запроса.
- Админка проверяет `ADMIN_IDS`; браузерная cookie использует `HttpOnly`, `Secure`, `SameSite=Strict`. Изменяющие запросы с cookie защищены проверками Origin и специального заголовка.
- Webhook сверяет секрет в пути и заголовке. Telegram update ID учитываются для защиты от повторной обработки.
- В рассмотренных запросах к БД значения параметризованы, а динамические таблицы и поля выбираются из фиксированных вариантов. Пользовательский текст в рассмотренных интерфейсах экранируется; CSP ограничивает скрипты.
- Новые фотографии читаются по ID сообщения с проверкой принадлежности чата пользователю. API групп не выдаёт сессию или access hash клиенту.
- Имена `.env`, файлов ключей и Telegram-сессий не найдены среди отслеживаемых файлов или в проверенной истории этих имён. Поиск шаблонов токенов бота и приватных ключей по текущим отслеживаемым текстовым файлам совпадений не дал. Это ограниченный поиск, а не полный аудит всех секретов за всю историю Git.

## Отдельный риск архитектуры: пользовательские Telegram-сессии

Elonbot хранит авторизованные MTProto-сессии личных аккаунтов. В отличие от одной команды «опубликовать это объявление», такая авторизация связывает последующие API-вызовы с аккаунтом пользователя. Это следует из [модели авторизации Telegram](https://core.telegram.org/api/auth#we-are-authorized).

Проверенный код выполняет ограниченный набор операций, но сама сессия не является разрешением только на выбранные группы. Злоумышленник, получивший выполнение кода в процессе приложения, сможет воспользоваться доступными ему сессиями. Шифрование базы полезно при отдельной утечке БД, но не защищает от процесса, который уже имеет ключ расшифрования. 2FA не превращает ранее выданную сессию в безопасный файл.

Практические меры: минимальные права службы и администраторов, закрытые конфигурация и резервные копии, контроль доступа к копиям ключа, подготовленный порядок отзыва сессий при инциденте. При росте сервиса имеет смысл вынести работу с пользовательскими сессиями в отдельный сервис с ограниченным интерфейсом. Это уменьшает поверхность доступа, но само по себе не отменяет риск компрометации этого сервиса.

Также необходимо ясно объяснять пользователю, зачем подключается аккаунт и как отозвать доступ. Помимо шаблонов в БД остаются объявления, черновики, обращения в поддержку и метаданные групп. Для них следует определить срок хранения и способ удаления аккаунта/данных. Это рекомендация по минимизации данных; оценка юридического соответствия не проводилась.

## Что остаётся проверить на VPS

Фактические версии Node.js, PostgreSQL и ОС, обновления, SSH, firewall, TLS, права `.env` и резервных копий, состав `ADMIN_IDS`, наличие посторонних процессов и восстановление из бэкапа. В коде сервер слушает `0.0.0.0`, поэтому внешний доступ к 8000 должен быть закрыт; для локального Caddy предпочтительно отдельное ограничение привязки к loopback. Полный дамп `.env` или токены для такой проверки не нужны.

Общий порядок работ: исправить обработку URL и привилегии обновления; исправить ограничения входов и очистку старых авторизаций; проверить настройки VPS и отзыв сессий; затем продолжать рекламный тест.
